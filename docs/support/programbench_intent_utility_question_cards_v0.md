# ProgramBench Intent / Utility Question Cards v0

Authority layer: support / experimental question-card overlay.

This note defines the first lightweight intent / utility branch for ProgramBench
reconstruction runs. It is deliberately procedural rather than schema-heavy.
The goal is to force a second, blind semantic descent from the visible task
brief into user jobs, utility promises, workflows, failure recovery, and data
ecology. The output is later reconciled back onto the concrete program ontology.

## 1. Blindness Rule

The intent / utility worker must not read:

```text
program-ontology artifacts
HOB activation or inherited ledgers
probe matrices
implementation notes
official eval failures
source code
postmortem audits
```

Allowed inputs:

```text
visible README / task prompt
publicly supplied examples in the prompt packet
declared task metadata
```

Public executable scout observations may be used only if the run explicitly
enters a later observation phase and the reconciliation worker records that
evidence as observation-derived rather than README-derived.

## 2. Output Shape

Each question card should produce rows like:

```yaml
utility_question_card_row:
  utility_ref: string
  source_evidence_refs: []
  user_job: string
  workflow_slice: string
  utility_promise: string
  positive_utility_questions: []
  negative_utility_questions: []
  implied_affordances: []
  data_or_resource_ecology: []
  failure_recovery_expectations: []
  ambiguity_or_scope_risks: []
  candidate_probe_pressure:
    - workflow_probe
    - mechanism_probe
    - negative_utility_probe
  evidence_posture:
    visible_spec_inference |
    visible_example_inference |
    public_observation_inference |
    unresolved_inference
```

The row must not name implementation functions, patch files, official tests, or
score expectations.

## 3. Universal Utility Questions

For every program-like task, answer:

1. What useful job would a real user hire this program to do?
2. What is the minimal successful workflow for that job?
3. What larger workflow does the tool sit inside before and after invocation?
4. What data, resources, state, or external systems does the user expect to bring?
5. What output does the user need to consume next, and by what kind of consumer?
6. What must the program preserve, transform, summarize, filter, or reject?
7. What must be easy to discover before the user knows the exact command?
8. What failures should help the user recover rather than silently mislead them?
9. What malformed, missing, ambiguous, or inconvenient inputs are normal for this
   utility class?
10. What negative behaviors would break the user's purpose even if a simple
    happy path works?

## 4. Workflow Composition Questions

For each user job, ask:

1. Does the job require inspection before transformation?
2. Does it require selection, filtering, joining, aggregation, or conversion?
3. Does it require multiple resources, multiple formats, or multiple modes in
   one workflow?
4. Does it require round-tripping or exporting to another tool?
5. Does the result need stable byte grammar, human readability, machine
   readability, or both?
6. Does the workflow depend on defaults, auto-detection, schema inference, or
   explicit user overrides?
7. Does the workflow have a common "oops" path that must be diagnosable?

## 5. Data Ecology Questions

For data-processing tools, ask:

1. What shapes can the user's data naturally take?
2. Which shapes are structured, semi-structured, line-oriented, tabular,
   nested, compressed, remote, streamed, or generated by another tool?
3. How does the user refer to resources: path, glob, stdin, URL, database,
   config, environment, query file, or inline literal?
4. What is the natural identity of a row, column, field, record, table, object,
   file, stream, or group?
5. What missing values, nulls, blank fields, mixed types, and malformed rows are
   plausible?
6. Which conversion must preserve type/domain semantics rather than only text?
7. Which defaults are dangerous if guessed incorrectly?

## 6. Control and Discoverability Questions

For CLI-like tools, ask:

1. How does a user discover available modes, formats, routes, and examples?
2. Which controls change the purpose of the command rather than only a setting?
3. Which controls are likely aliases, no-ops, pass-through, or mutually
   exclusive?
4. Which controls affect input interpretation, output interpretation, resource
   routing, diagnostics, or exit posture?
5. What happens when controls are missing, duplicated, ordered differently, or
   combined with incompatible modes?

## 7. Negative Utility Questions

For each utility promise, ask:

1. What would make the output look plausible but be semantically wrong?
2. What would cause the program to act on the wrong resource or wrong schema?
3. What would make a downstream consumer fail because byte grammar drifted?
4. What would hide a user error behind an empty result?
5. What would turn an inspection mode into a transformation mode or vice versa?
6. What would make a failure unrecoverable because the diagnostic omits the
   useful discriminator?

## 8. Reconciliation Handoff

The intent / utility branch does not close program behavior. It hands rows to
the reconciliation worker. Every row must later receive one of:

```text
mapped_to_existing_program_node
creates_candidate_program_node
out_of_scope_with_evidence
unresolved_program_mapping_blocker
```

Implementation, probe locking, and HOB closure are blocked for any utility row
that remains unmapped without an explicit out-of-scope or blocker posture.
